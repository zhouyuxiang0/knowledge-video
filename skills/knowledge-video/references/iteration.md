# 复盘与维护

目标是减少同类返修，让下一期更早得到可靠画面，不是把每次制作过程变成更长的规章。

## 每次返修或交付后

在当期工程的既有 QA/复盘中保留短记录：

| 字段 | 内容 |
|---|---|
| 反馈与版本 | 用户原意、涉及镜头/时间、可定位的实际成片 |
| 实际缺陷 | 看见了什么；区分缺陷、个人风格偏好和证据缺口 |
| 原因 | 为什么旧流程没提前发现；不要只写“检查不够” |
| 修正 | 改了什么、波及哪些调用/镜头、保留了什么已确认输入 |
| 新检查 | 最早在哪个阶段、用什么实际证据能拦住同类问题 |
| 结果与边界 | 新版本复看结果、用户是否接受，以及尚未验证部分 |

下一期开始时只读取相关案例，并把已证实的方法放进当期样段或验收。案例里的声音、配色、人物比例、引擎和时长属于具体项目；没有用户要求，不升级为所有视频必须遵守的偏好。

## 怎样更新 skill

- 用户已授权持续维护时，在每期真实反馈/新失败模式出现后更新相关段落；无此授权时记录当期发现并提出维护建议。
- 优先修正现有规则，删除过时假设。只有会改变下一次决定的内容才进入通用 skill；一次性台词、镜头编号和完整日志留在项目复盘。
- 新规则写清触发条件、行动与可观察证据。例如“共享核查画面改动后检查所有调用的语义”，比“以后更认真”可执行。
- 区分已发生的失败、推断的原因和待验证的修法。用户否定足以撤销对应放行，不能反过来证明新写法有效；新稿尚未复看或接受时保留这一状态。不把一次通过当作稳定性证明，跨片观察是否减少了同类返修。
- 持续维护指每次相关创作/反馈后的迭代，不暗示有无人值守的后台工作。用户明确要求定时或监控时再设置对应机制。

## 维护后验证

归档旧工程前，按项目已约定且用户授权的保留范围处理。将后续仍依赖的配音参数、参考路径、用户决定与通用经验移到共享入口，修正调用和链接；不要把删除后的成片、试音或单期脚本继续列为有效默认。单期媒体是否删除由用户和项目约定决定，不在通用 skill 中强制统一。

检查入口能找到新规则，链接和现有脚本路径仍可用。将规则放到不同题材和合理形式下复读：是否仍支持没有角色的机制解释、没有笑话的严肃叙述等任务，还是误把本次成功或失败的表面形式规定成唯一写法？优先沿用现有安装结构；源包与实际加载副本存在两份时，同步本次改动并核对摘要，勿仅修改未加载的副本。

运行 skill 格式检查；复杂流程更改可做一次独立前向试用：提供真实风格的请求、原始材料及隔离输出位置，不给期望答案。检查它是否能作出有依据的决定，是否保留用户授权/确认范围，是否诚实区分证据层级；不要仅匹配措辞或标题。

只根据试用中实际暴露的问题调整规则。验证完成后记录适用范围；不为同一份未变更内容反复评审或扩大改造。
